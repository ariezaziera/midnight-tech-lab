## Publication safety assessment

**Existing protection:** import-time `validateContent` rejects missing approval on published records, invalid identity/duplicate IDs/unknown references, missing published role/overview, malformed media metadata, unapproved outcomes and unsafe/unapproved links. `isPublished` requires status plus both approval flags and a nonblank source. Drafts are excluded from selection/detail routes; related cards are filtered again by published status. Media and links are approval-filtered at rendering too.

**Limits that intake must address:**

1. A flag/source string records an owner decision; it cannot prove accuracy, ownership, permission or confidentiality clearance. Do not put private correspondence, credentials or restricted evidence in committed records or assets. Draft status does not make a repository file private.
2. Published validation requires role and overview, but not problem, contribution, process, solution, nonempty tools or nonempty categories. These are stronger proposed packet requirements below, not existing runtime guarantees. Outcomes and media are optional, appropriately allowing honest omission.
3. Media validation checks local-path shape, positive integer dimensions, alt, rights, provenance and approval. It does **not** read files, decode images, compare actual dimensions, measure size, inspect redactions or verify licenses. A path under `public/` would be directly accessible irrespective of record status. Only approved public derivatives should be copied there.
4. `safeLink` is a scheme/shape and approval check, not a destination ownership, redirect, availability or permission check. It permits HTTPS, mailto, tel and local paths. Project links should be manually verified public HTTPS destinations; omit unpermitted/private/missing links. No live demo or repository is mandatory.
5. Category membership validates existence, not Development suitability. Related references validate existence, not publication eligibility; rendering suppresses unpublished related work. Start with `relatedSlugs: []`, and do not select an exhibit from an unfiltered record array.
6. Generic editorial components accept supplied objects; route/selectors form the publication boundary. A2 must consume an explicit approved public projection, never pass the full content object, draft narrative or private approval evidence into a client/scene bundle.

**Assessment:** the current empty inventory is guarded appropriately for its existing use. It is not yet evidence that an authentic packet, media file or scene mapping is safe. No application defect is being fixed in this planning task.

## Minimum viable authentic project packet

Owner can return this checklist for **one** project. Supply exact approved public wording/files plus a non-sensitive approval reference; keep private supporting evidence outside Git. Approval is item-specific, not inferred from candidate names, repository access or milestone acceptance.

- [ ] **Identity:** approved public name, stable lowercase hyphenated slug (not `placeholder`), concise summary and fuller overview. Confirm whether this is personal, academic, employment or client work; approve public organization names only if needed and permitted.
- [ ] **Classification:** approve category ID/label (recommend `development` / “Development”, still proposed), actual project type, and why this project belongs in the Development journey. Add other categories only where justified.
- [ ] **Role and attribution:** actual role, precise personal contribution, collaboration boundaries and third-party contributions. Do not imply sole authorship of team work. No employment dates, seniority or skills are inferred.
- [ ] **Narrative:** problem/context, solution/deliverables and a short process sequence including at least one real technical decision, its reason and relevant limitation. Separate what the owner built from tools/platform capabilities. Supply a short approved contribution/decision excerpt suitable for future HTML beside the exhibit; reuse the case study rather than create conflicting claims.
- [ ] **Verified tools:** list only technologies actually used by the owner in this project, with confirmation source. If none may be disclosed, explicitly approve omission and the text-first explanation; never substitute the portfolio's own Next/Three stack or inferred logos.
- [ ] **Outcome:** supply a verifiable qualitative result or explicitly approve omission. Quantified claims require their own approved source, scope and context. No invented success numbers, users, performance, clients, testimonial or completion date is required.
- [ ] **Media choice:** supply at least one authentic screenshot/static artifact approved for the intended HTML use and, separately, any future 3D surface use; **or explicitly approve a text-first A2 exhibit**. Media is not mandatory if that exception is approved. A text-first choice does not authorize A2 implementation.
- [ ] **Per-image packet:** approved derivative file, original/source identifier, authorship and copyright holder, permission/license and attribution wording, public-use/redaction/crop restrictions, dimensions, format/encoded size, descriptive alt text and useful public provenance. Remove secrets, personal data, confidential UI and restricted third-party imagery before ingestion. Obtain permission for depicted people/client/employer work where applicable. No concept-board crop or synthetic test image may stand in for project evidence.
- [ ] **Links (optional):** exact public HTTPS repository/demo URLs, labels, ownership/permission confirmation and manual destination check. No tokens, signed private URLs, login-only repositories or fictional demo actions. If unavailable, approve empty links.
- [ ] **Publication sign-off:** approve the exact title/summary/narrative/tools/category/outcome/media/link revision for public presentation in the prototype, with non-sensitive source reference and date. Approve any later redacted/cropped version again if its meaning or permission changes. Public-presentation permission does not authorize deployment.

Mapping: narrative → `caseStudy`; technologies → `tools`; media → `media`; approved external destinations → `links`; public classification → `categoryIds` and optionally `projectType`. Record-level approval covers factual narrative/tools/role; each media/link/outcome retains its existing separate `Approval`. No schema extension is proposed merely to rename these fields.

Full biography, global skills inventory, portrait, CV/socials, services, contact destination, additional projects and personal artwork are **not** prerequisites for this single-project packet. Contact stays visibly incomplete. A complete recruiter/client inquiry or release-ready portfolio must not be claimed without those separately necessary inputs.
